Understanding the problem

Q. What is Stripe?
- Payment processing systems like Stripe allow business 
(referred to throughout this breakdown as merchants) 
to accept payment from customers, without having to 
build their own payment processing infrastructure. 
Customer input their payment details on the merchant's 
website, and the merchant sends the payment details 
to Stripe. Stripe then processes the payment and returns 
the result to the merchant.
 ^K5uw00el

* Functional Requirements

1. Merchants should be able to initiate payment requests (charge a customer
for a specific amount).
2. Users should be able to pay for products with credit/debit cards.
3. Merchants should be able to view status updates for payments (Ex: pending, 
success, failed).

* Functional Requirements - Good to have

1. Customers should be able to save payment methods for future use.
2. Merchants should be able to issue full or partial refunds.
3. Merchants should be able to view transaction history and reports.
4. Support for alternative payment methods. (Ex: Bank transfers, Digital wallets)
5. Handling recurring payments (subscriptions)
6. Payouts to merchants.

* Non Functional Requirements

[10k TPS at peak load]

1. System should be highly secure
2. Strong Durability (can't lose transactions) - System should guarantee 
  durability and auditability with no transaction data ever being lost, even in 
  case of failures.
3. Transaction safety and financial integrity (no double charge etc) - System 
  should guarantee transaction safety and financial integrity despite the inherently 
  asynchronous nature of external payment networks.
4. System should be scalable to handle high transaction volume (10,000+ TPS) 
   and potentially bursty traffic patterns (e.g., holiday sales).
 ^Jdf2OUU2

Core Entities

Merchant
- This entity will store information about the businesses using our 
  payment platform, including their identity details, bank account 
  information, and API keys.

PaymentIntent
- This represents the merchant's intention to collect a specific amount 
  from a customer and tracks the overall payment lifecycle from creation 
  to completion. It owns the state machine from created → authorized 
  → captured / canceled / refunded, and enforces idempotency for 
  retries.
- Too much technical above, simple explanation below
Ex: When a user clicks on checkout page of hello interview, request goes
to Stripe that charge the User X on Hello interview for Amount 'Y'. Still the 
Credit card/ Debit card/ Bank account number is not given. Just a payment
request is made (a database entry is made), this is similar to RideRequest
object in Uber design where we make a object as soon as user clicks on request 
ride but still the ride is not booked or confirmed

Transaction
- This represents a polymorphic money-movement record linked back to
  one PaymentIntent. Types include Charge (funds in), 
  Refund (funds out), Dispute (potential reversal), and 
  Payout (merchant withdrawal). Each row carries amount, currency, 
  status, timestamps, and references to both the intent and the 
  merchant. For simplicity, we'll only be focused on Charges as everything 
  else is out of scope.
 ^PG7jSWL3
