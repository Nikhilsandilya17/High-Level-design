2. LSM Trees
- With B-trees, each write means finding the right leaf page, reading it into memory, updating it, and writing it back to disk. For a few thousand writes 
per second, this works fine. But when you're processing 100,000 writes per second, those random disk seeks become a bottleneck. It's like trying to 
update a filing cabinet where you need to find and modify individual folders scattered throughout - eventually, you spend more time searching than 
actually storing data.

# Working of LSM trees :-
 ^jXYgfn0G

1. Memtable (Memory Component): New writes go into an in-memory structure called a memtable, typically implemented as a sorted data structure like a 
red-black tree or skip list. This is extremely fast since it's all in RAM.

2. Write-Ahead Log (WAL): To ensure durability, every write is also appended to a write-ahead log on disk. This is a sequential append operation, which 
is much faster than random writes.

3. Flush to SSTable: Once the memtable reaches a certain size (often a few megabytes), it's frozen and flushed to disk as an immutable 
Sorted String Table (SSTable). This is a single sequential write operation that can write megabytes of data at once.

4. Compaction: Over time, you accumulate many SSTables on disk. A background process called compaction periodically merges these files, 
removing duplicates and deleted entries. This keeps the number of files manageable and maintains read performance. ^HuTj2cVp

# Impact on Read performance

- Remember how B-trees could find any record with just 2-3 disk reads? With LSM trees, the story is different.
- When you query for a specific key, the database must check multiple places:
1. First, the memtable: Is the data in the current in-memory buffer?
2. Then, immutable memtables: Any memtables waiting to be flushed?
3. Finally, all SSTables on disk: Starting from the newest (most likely to have recent data) and working backwards
This means a single point query might need to check dozens of files in the worst case. It's like searching for a document that could be in your 
desk drawer, filing cabinet, or any of several archive boxes. And you have to check them all. ^6hOiuYw9

Obviously, this would make LSM trees almost unusable for any workflow requiring reasonable read performance. So to mitigate this problem, 
LSM trees typically employ several optimizations:

1. Bloom Filters: Each SSTable has an associated bloom filter - a probabilistic data structure that can quickly tell you if a key is definitely NOT in 
that file. This lets you skip most SSTables without reading them. If the bloom filter says "maybe", you still need to check, but it eliminates the 
definite misses.

2. Sparse Indexes: Since SSTables are sorted, they maintain sparse indexes that tell you the range of keys in each block. If you're looking for 
user_id=500 and an SSTable only contains keys 1000-2000, you can skip it entirely.

3. Compaction Strategies: Different compaction strategies optimize for different workloads. Size-tiered compaction minimizes write amplification 
but can lead to more files to check. Leveled compaction maintains fewer files but requires more frequent rewrites. ^phKZoVmf

##  Geospatial Indexes: Interview Cheatsheet

### 1. The Problem: Why Standard B-Trees Fail

If you want to find "restaurants within 5 miles," a standard database index on Latitude and Longitude breaks down.

* B-Trees are 1-Dimensional: They excel at sorting flat lists (like A-Z or 1-100).
* Location is 2-Dimensional:  If you search by Latitude first, you get a massive horizontal strip wrapping around the entire globe.
* The Intersection Problem:  The DB has to fetch all restaurants in the Latitude strip, all restaurants in the Longitude strip, and merge them. This is incredibly 
slow and inefficient for proximity queries.

### 2. The Solution: Geospatial Indexes

We need a way to map 2D space (grids) into 1D data structures (strings or numbers) so our databases can query them quickly. The three most common approaches are:

1. **Geohash** (Used by Redis)
2. **Quadtree**
3. **R-Tree** (Used by PostgreSQL/PostGIS)

### 3. Deep Dive: Geohash

Geohash solves the 2D-to-1D problem by continuously dividing the map into quadrants and converting those quadrants into a short, queryable string.

**How it's generated:**

1. The Binary Halving:** The world is cut in half vertically (Longitude: 0 for left, 1 for right) and horizontally (Latitude: 0 for bottom, 1 for top). By alternating 
these cuts, you zoom in closer to a specific location, generating a long binary string (e.g., `011010101...`).
2. The Base32 Compression:** Because a 40-bit binary string is impossible to manage, Geohash groups the bits into chunks of 5 and converts them into a 
Base32 alphanumeric character.

* *Why Base32?* It compresses the string 5-to-1. It is URL-safe, easy to read, and intentionally excludes confusing characters (like `a`, `i`, `l`, `o`).

**The Result:** A location becomes a simple string like `9q8yyk`.
* `9q8y` = San Francisco
* `9q8yy` = The Mission District
* `9q8yyk` = A specific city block

### 4. Database Implementation & The "Edge Case"

**The Elegance (Prefix Matching):**
Because Geohashes are just strings, you don't need a special database engine. You can put them straight into a **Standard B-Tree Index**.

* To find restaurants near a user at `9q8yyk`, the database simply executes a lightning-fast range scan for all strings starting with that prefix (`LIKE '9q8yy%'`).

**The Edge Case (Boundary Crossings):**
What if two restaurants are 10 meters apart, but they sit exactly on the dividing line of a major grid quadrant?

* The Issue:** Their Geohashes might look completely different (e.g., one starts with `9`, the other starts with `d`).
* The Fix:** When doing a radius search, the database doesn't just search the user's Geohash block; it mathematically calculates and searches the prefixes of the 
8 immediately adjacent blocks** to ensure no nearby locations are missed. ^Qfoi6bOp
