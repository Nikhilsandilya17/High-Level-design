# The Two-Phase Commit (2PC) Protocol

The Two-Phase Commit (2PC) is a standardized protocol used in distributed systems to implement atomic transactions. 
Its primary goal is to ensure that a transaction is either committed by all participating nodes or aborted by all nodes, 
maintaining data consistency across different databases or services.

Think of it as the All or Nothing rule for distributed data.

# The Roles :-

To understand 2PC, you must identify the two types of actors involved:

1. The Coordinator (Transaction Manager): The central node that manages the transaction logic. It asks the 
participants if they are ready and makes the final decision.
2. The Participants (Cohorts/Resource Managers): The distributed nodes (databases, microservices) that actually hold 
the data and perform the write operations.
 ^JwYouECD

# How It Works: The Two Phases

As the name implies, the protocol splits the commit process into two distinct phases.

- Phase 1: The Prepare Phase (Voting)

In this phase, the system determines if the transaction *can* be performed.

1. Request: The Coordinator sends a `PREPARE` message to all Participants. This asks: *"Are you ready to commit this transaction? Do you have 
the necessary locks and resources?"
2. Action: Each Participant attempts to execute the transaction locally (writing to a transaction log) but does not commit yet.
3. Vote:
* If successful, the Participant votes Yes (Ready).
* If it fails (e.g., deadlocks, disk error), it votes No (Abort).

- Phase 2: The Commit Phase (Completion)

The Coordinator collects the votes and determines the outcome.

Scenario A: Success (All voted Yes)
1. The Coordinator sends a `COMMIT` message to all Participants.
2. Participants make the changes permanent and release their locks.
3. Participants send an acknowledgment (ACK) back to the Coordinator.


Scenario B: Failure (At least one "No" or Timeout)
1. The Coordinator sends a `ROLLBACK` (Abort) message to all Participants.
2. Participants undo any local changes and release locks.
3. Participants send an acknowledgment (ACK) back. ^4fqAW5Jy

# Real-World Analogy: A Wedding Ceremony

The 2PC protocol is often compared to a standard wedding ceremony:

- The Coordinator: The Officiant.
- The Participants:  The Couple.
- Phase 1 (Prepare):  The Officiant asks, "Do you take this person...?" (Request). The individuals answer "I do" 
(Vote Yes).
- Phase 2 (Commit): Only after hearing "I do" from both, the Officiant says, "I now pronounce you..." (Commit). 
If one person says "I don't" or runs away, the wedding is off (Rollback). ^37yUeIog

# Advantages and Disadvantages

1. Consistency | Pro: It guarantees strict ACID properties. The data will remain consistent across all nodes. |
2. Blocking | Con: It is a "blocking" protocol. If the Coordinator crashes after sending the `PREPARE` request, Participants are left 
    "hanging," holding locks on resources indefinitely until the Coordinator recovers. |
3. Latency | Con: It is slow. The transaction cannot finish until the slowest Participant has responded. This makes it poor for 
    high-performance systems. |
4. Single Point of Failure | Con: If the Coordinator fails, the whole process halts. 

# Summary

2PC is the industry standard for scenarios where **data integrity is more important than speed** (e.g., transferring money 
between two different bank databases). However, due to its blocking nature, modern high-scale microservices often prefer 
"Eventual Consistency" patterns (like Sagas) instead. ^TtusX5i2
